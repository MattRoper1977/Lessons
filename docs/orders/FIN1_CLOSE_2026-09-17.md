#### Two routes parked, and the measurement that parks them

`#565` named 27 routes and FIN1-Z named 28. Twenty-six are stamped. **Both exclusions have the same
cause, and it is the pinned generator, not the pages.**

- **`Games/Glitch_Clash.html`.** The pinned generator locates the body tag by substring. This page
  carries the literal text `<body>` inside a CSS comment on line 20, so the region lands at line 21
  **inside the `<style>` block**, where it never runs — and `--check` stays green, because it
  compares against the same mistake. Measured: all 35 candidate routes were stamped in a scratch
  worktree and each region's position compared with the insert point an HTML parser derives. 34 land
  at the real body tag. This one does not.
- **`Games/Charcoal.html`.** Measured by CI, not by inspection. Run 35253113325, *"The way out of a
  game is keyboard-reachable — both estates"*: 1340 assertions passed, 3 failed, all three this page
  at 390, 768 and 1440 px — `homepage control is reachable by Tab · presses: null`. The control was
  reachable before the stamp. The pinned generator's `armWayOut()` arms a Tab handoff from whatever
  `primary()` returns, with no guard for the case where that element **is** the way-out control or
  contains it.

Site `main`'s generator already fixes both — a parser-derived insert point (`_BodyFinder`, written
for this exact page) and the missing `armWayOut` guard, with the exit and home controls excluded from
`primary()` outright. It is not the generator pinned by the workflow. Re-pinning the canonical owner
re-cuts the region on **every** route that already carries one, which is a release decision and not a
stamp. Both routes are parked for that decision. See **Open items**, item 2.

This also answers, with a number, the product question `#565` raised: eleven of the shelf routes show

### D — the approved mark in the Play footer

The footer carried the words "Made by Matt Play" and no mark. It now carries the same approved
M/circle/star Matt supplied for PLAY-D1 (`bfef5b1e…792a`) — same verified bytes, same served URL as
the header, no second asset, no recolour, no crop — inside a home link named by the words beside it.

| requirement | how it is met | measured |
|---|---|---|
| alt rules | `alt=""`; the link is named by its text, so naming the image too would read the brand twice | asserted at all four widths |
| ≥24×24 target | rendered 32×32, with a 24×24 CSS floor that holds even if the mark never loads | `32x32` at 320, 390, 768, 1280 px |
| focus-visible | the shelf's shared 3px mint `a:focus-visible` ring, not a new rule | `{focused:true,width:"3px",style:"solid"}` |
| no layout shift | `width`/`height` in the markup **and** in the CSS, so the box exists before the JPEG decodes | attributes asserted present |

**Proved red three ways before pushing:** an `alt` repeating the link's words → the decorative
assertion fires; `width`/`height` dropped → the layout-shift assertion fires; sized 20×20 →
`footer mark 20x20 is under the 24x24 WCAG 2.2 minimum`.

**And one thing the criterion as written let through.** Built to ">=24x24" the link measured 208×32,
which satisfies WCAG 2.2 and fails **this shelf**: `--tap` is 44px, every footer nav link already
carries `min-height:var(--tap)`, and `check.cjs` `targets()` enforces 44 on every visible control at
390px. CI found it — `390-targets-44px-closed-drawer-sheet`, naming the element and its 208×32 box —
and the link now takes `--tap` while the mark stays 32×32 inside it. **The 44px floor is now asserted
beside the 24×24 one at the point of measurement**, so a weaker criterion cannot again be satisfied
while the estate's own gate rejects the result. Measured after the fix: link 208×**44**, computed
`min-height` 44, at all four widths.

The reproduction that found it needed the third and last local build. `check.cjs` launches
`channel: "chrome"`; this container has only bundled Chromium, so 43 of its 44 checks were run
locally and one — `accepted-preview-playback-seeking-pause-close` — is **UNMEASURED here**, not
passed. That is stated rather than assumed: bundled Chromium answers
`canPlayType('video/mp4; codecs="avc1.42E01E"')` with `""`, and the accepted previews are `.mp4`. CI,
on real Chrome, is the measurement for that one.

### F — the serve witness, red since 14 September

Every run in the window says the same thing. Tabulated rather than generalised from the newest:

| run | date | verdict |
|---|---|---|
| 34757958618 | 13 Sep | success |
| 34853904311 | 14 Sep | failure |
| 34970524345 | 15 Sep | failure |
| 35097002140 | 16 Sep | failure |
| 35222166402 | 17 Sep | failure |

All four failures have the same shape: site WITNESSED 4/4, lessons WITNESSED 24/24, apps WITNESSED
1/1, **games RED 0/2** —

```
RED  https://madebymatt-play.uk/              http=200
     served=109606B/67dac020  expected=109606B/67dac020  served from another origin
RED  https://madebymatt-play.uk/Games/games.json  http=200
     served=34095B/ddf5b400   expected=34095B/ddf5b400   served from another origin
```

**The served bytes equal the publication's bytes on both subjects.** The red is the origin rule
alone: the final URL's host differs from the one requested. Whether that is a benign apex-to-host
redirect or a genuinely wrong origin turns entirely on what that final URL is — and the summary never
printed it, though the row has carried `final_url` in its JSON all along. The artifact host is
unreachable from the agent container and so is either origin, so the instrument is the only thing
that can say.

**What was done, and what deliberately was not.** The summary line now names the origin it landed on.
No verdict, no exit code and no rule changed: the origin check still reds exactly when it did.
Loosening a witness on a hypothesis is how a witness stops being one. `summary_line()` is covered by
the tool's own `--self-test`, which requires the redirect case to carry `landed=` and the
non-redirect case not to; drop that branch and the self-test fails.

**And then it answered itself.** Run 35273878480, the first red since the field was added:

```
games  RED  0/2 subjects  main 909c29c2
  RED  https://madebymatt-play.uk/                  http=200
       served=109780B/69d71abc  expected=109780B/69d71abc
       landed=https://www.madebymatt-play.uk/                  served from another origin
  RED  https://madebymatt-play.uk/Games/games.json  http=200
       served=34095B/ddf5b400   expected=34095B/ddf5b400
       landed=https://www.madebymatt-play.uk/Games/games.json  served from another origin
```

**It is the apex-to-`www` redirect, and the bytes are identical.** That was the hypothesis; it is now
a measurement, and the added reporting is what produced it rather than an assumption. Note too that
`/` moved from `109606B/67dac020` to `109780B/69d71abc` and still equals its expected digest
exactly: that is the footer mark from **D**, correctly served.

**The ruling is Matt's, not mine.** Accepting a `www` host of the same registrable domain changes
what the origin rule accepts, and FIN1-Z F permits a recommended ruling only if it loosens nothing.
So the recommendation is recorded and NOT applied: *treat a redirect that stays within the
publication's own registrable domain as MATCH when the bytes match, and keep RED for every other
host.* Until Matt rules, the games rows stay red, correctly, and the reason is now legible in one
line instead of unreadable behind a blocked artifact.
